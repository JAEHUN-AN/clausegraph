# 039 — 권한 게이트를 걸고, 어디에 걸어야 하는지를 쟀다

[notes/037](037-jd-gap.md)에서 **권한 기반 데이터 접근 제어**는 판정이
`없음`이었다. 담당업무와 우대사항 양쪽에 있는데 개념 자체가 없었다 —
MCP 도구 10개가 무인증이고, 어느 도구든 전 상품·전 판본을 돌려줬다.

그런데 이 프로젝트에서 권한이 흥미로운 이유는 따로 있다. **경로가 셋이다**
— 그래프(Neo4j), 벡터(pgvector), MCP. 그리고 이 프로젝트는 경로가 여럿일 때
무슨 일이 생기는지를 이미 비싸게 배웠다.

> **감싸는 줄 알았던 것이 두 번째 구현이었다.** (notes/023)

MCP 도구가 심사 경로를 감싸는 줄 알았는데 버전 선택을 자기가 다시 하고
있었고, 가입일×상품 1,472쌍 중 32쌍이 어긋났다. 권한에서 같은 일이
일어나는지, 일어난다면 얼마나 새는지를 쟀다.

## 축을 상품 하나로 잡았다

지급심사에서 권한이 실제로 갈리는 축이다. 실손 심사자는 실손 계열을 보고,
자동차 손사는 자동차보험을 본다.

**판본은 축이 아니다.** "2025년 약관은 보되 2026년은 보지 말라"는 권한은
업무에 없다 — 판본은 계약이 정하는 것이지 사람이 정하는 것이 아니다.

**보장종목까지 내려가지 않았다.** 축을 하나 더 내리면 전수 조합이 커지는데,
그 축에서 권한이 갈리는 업무를 찾지 못했다. 근거 없이 정밀하게 만드는 것은
정밀한 것이 아니다.

상품 16개를 넷으로 나눴다 — 실손심사(8) · 자동차손사(1) · 생명제휴(1) ·
일반손보(5).

## 거절과 침묵을 가른다

같은 권한인데 두 가지로 답해야 한다.

| 경로 | 스코프 밖이면 | 왜 |
|---|---|---|
| **이름으로 지목** (`find_coverage("자동차보험", …)`) | **거절한다** | "조항이 없다"와 "볼 수 없다"는 다른 말이다. 앞의 말로 뭉개면 심사자가 없는 약관을 찾아 헤맨다 |
| **검색으로 걸림** (`search_vector("…")`) | **조용히 뺀다** | 어느 상품이 나올지 호출부가 미리 모른다. "검색했는데 권한 오류"는 쓸모가 없다 |

이 둘을 섞으면 안 된다. 섞으면 검색 한 번에 권한 오류가 뜨거나, 지목한
상품이 빈 결과로 돌아온다. 둘 다 사용자를 헷갈리게 한다.

## 빈 스코프는 '전체'가 아니다

`Principal(products=frozenset())`은 **아무것도 못 본다.** 비어 있음을
전체로 읽는 기본값은 조용한 권한 상승이고, 이 프로젝트는 그 모양을
이미 한 번 겪었다 — notes/027에서 `already_paid_this_year`의 `0`을
"모른다"가 아니라 "올해 받은 것이 없다"로 읽어 과다지급을 냈다.

전체를 주려면 `Principal.everything()`으로 **명시**해야 한다.

## 얼마나 샜나

주체 4 × 문항 18. 게이트가 유일한 차이라서 두 값의 차가 곧 막은 양이다.

| 경로 | 게이트 전 | 게이트 후 | 거절 |
|---|---:|---:|---:|
| `search_vector` | 546 | **0** | — |
| `search_lexical` | 515 | **0** | — |
| `search_graph` | 5,775 | **0** | — |
| **`search_hybrid`** | **15,410** | **0** | — |
| `find_coverage` | 63 | **0** | 45 |
| `enumerate_exclusions` | 1,296 | **0** | 45 |
| **합계** | **23,605** | **0** | |

### 누수는 검색에서 새는 게 아니라 그래프로 번진다

`search_hybrid` 하나가 전체 누수의 **65%** 다. 벡터 단독 546건의 **28배**다.

이유는 `search_hybrid`의 구조에 있다. 상품 목록이 호출부가 아니라 **벡터
결과에서** 나온다.

```
seeds    = search_vector(...)                      # 스코프 밖 1건이 섞임
products = {hit.product for hit in seeds}          # 그 상품이 목록에 들어감
merged  += search_graph(driver, products, ...)     # 그 상품의 면책이 통째로
```

**씨앗 한 건이 조항 수십 개가 된다.** 그래프 다리는 "그 상품의 면책을
빠짐없이" 가져오도록 만들어져 있고(notes/008), 그 성질이 여기서는 증폭기로
작동한다. recall을 만든 구조가 누수도 만든다.

## 어디에 걸어야 하는가 — 이게 진짜 질문이었다

게이트를 어디까지 걸었을 때 얼마가 남는지를 다섯 상태로 쟀다.

| 시나리오 | vector | lexical | graph | hybrid | agent | 합계 |
|---|---:|---:|---:|---:|---:|---:|
| 게이트 없음 | 546 | 515 | 5,775 | 15,410 | 1,296 | **23,542** |
| **에이전트 층만** | 546 | 515 | 5,775 | 15,410 | 0 | **22,246** |
| 벡터만 | 0 | 515 | 5,775 | 0 | 1,296 | **7,586** |
| 검색 경로 전부 | 0 | 0 | 0 | 0 | 1,296 | **1,296** |
| 전부 | 0 | 0 | 0 | 0 | 0 | **0** |

**에이전트 층에만 걸면 94.5%가 그대로 샌다.** 그런데 에이전트 층은 심사
경로다 — "판정에 권한을 걸었다"고 말하기 가장 쉬운 자리이고, 걸고 나면
`adjudicate`가 남의 상품을 거절하므로 **막은 것처럼 보인다.** 실제로는
스무 배가 넘는 조항이 검색 도구로 그대로 나간다.

notes/023이 말한 것이 정확히 이것이다. 감싸는 줄 알았던 것이 감싸지 않는다.

한 줄이 흥미롭다. **벡터만 걸면 hybrid가 덤으로 0이 된다** — 씨앗이
깨끗해지면 증폭할 것이 없기 때문이다. 하지만 `search_graph`를 직접 부르는
경로는 5,775건이 그대로 남는다. **증폭기를 막는 것과 원천을 막는 것은
다른 일이고, 둘 다 해야 한다.**

## 그래서 게이트를 질의에 걸었다

호출부가 아니라 **데이터가 나오는 질의 자체**에 건다.

```sql
AND (%s::text[] IS NULL OR product = ANY(%s::text[]))
```

`LIMIT`보다 **앞**이다. 뒤에서 걸러내면 k개를 뽑아 그중 스코프 밖을 버리게
되어, 권한이 좁을수록 결과가 조용히 적어진다.

그리고 `principal`을 **키워드 필수**로 만들었다. 기본값을 두면 넘기는 것을
잊어도 통과하고, 잊었다는 것이 드러나지 않는다. 지금은 잊으면 `TypeError`다.

```python
def find_coverage(driver, product, version, *, principal: Principal) -> ...
```

캐시는 **권한 검사 뒤에** 본다. 앞에 두면 다른 주체가 데워 둔 값을 권한
없는 주체가 그대로 받는다 — 캐시는 권한을 기억하지 않는다.

테스트로 고정했다. `test_every_data_path_requires_a_principal`은 조항을
돌려주는 함수 10개의 시그니처를 검사해, 기본값이 생기면 실패한다.

## 덤으로 닫은 것 — 도구 경계의 오류 처리

notes/037에서 오류 처리가 `부분`이었던 자리다. 외부 LLM 호출은 촘촘한데
(`llm/client.py`) MCP 도구 경계에는 `try/except`가 **하나도 없어**, Neo4j가
죽으면 스택트레이스가 그대로 MCP 클라이언트로 나갔다.

권한 거절도 예외라서 이걸 먼저 고쳐야 했다. 도구 10개에 `@guarded`를 걸어
`AccessDeniedError`는 "권한 없음: …"으로, 나머지 예외는 로그에 남기고
호출한 쪽에는 내부 사정을 흘리지 않는다. 발동 수는 `REGISTRY`에 센다.

`test_every_mcp_tool_is_guarded`가 `@mcp.tool()` 수와 `@guarded` 수를
맞춰 둔다.

## 이것은 인증이 아니다

**분명히 적어 둔다.** MCP stdio는 호출자를 확인하지 않는다. 스코프는
환경변수(`CLAUSEGRAPH_SCOPE`)로 정하고, 이 값은 **악의적인 호출자를 막지
못한다.** 정직한 호출자가 무엇을 보게 되는지를 정할 뿐이다.

실제 배포라면 전송 계층에서 주체를 확인해 **요청마다** `Principal`을
만들어야 한다. 지금 구조는 그걸 받을 자리가 이미 있다 — `principal()`이
돌려주는 값을 요청별로 바꾸면 된다.

기본값을 `everything`으로 둔 것도 적어 둔다. 조용한 기본값이라는 것을
알면서 그렇게 했다 — 빈 스코프를 기본으로 하면 설정을 잊었을 때 도구가
전부 "권한 없음"을 돌려주고, 그게 설정 문제인지 데이터 문제인지 구분되지
않는다. 대신 시작할 때 무엇으로 열렸는지 로그에 남긴다. **`Principal`
자체의 기본값은 여전히 "아무것도 못 봄"이고**, 느슨한 것은 MCP 서버의
설정 해석 한 곳뿐이다.

## 남은 것

- **세션이 주체를 기억하지 않는다.** `agents/session.py`의 `STORE`는
  `session_id`로만 가른다. 지금은 서버 전체가 스코프 하나라 문제가 없지만,
  요청별 주체로 가면 A가 만든 판정을 B가 `follow_up`으로 읽을 수 있다.
  주체를 세션 키에 넣어야 한다.
- **판본 축을 안 걸었다.** 위에 적은 이유로 지금은 맞다고 보지만, 재보험이나
  위탁 심사처럼 "특정 시점 계약만" 보는 업무가 있으면 축이 하나 는다.
- 누수 측정은 **측정한 경로에 대해서만** 0이다. 경로를 새로 더하면 그 경로도
  더해야 하고, 더하는 것을 잊으면 이 측정이 못 잡는다. 시그니처 테스트가
  그 빈틈을 일부만 메운다.
