# 027 — 모든 청구를 그 해 첫 청구로 보고 있었다

notes/017부터 세 노트에 걸쳐 "누적 상태가 필요한 한도는 미구현"이라고
적어 두었다. 그 자리를 채우러 갔다가 그것이 **미구현이 아니라 잘못
구현되어 있었다**는 것을 봤다.

## 기본값 0이 곧 가정이다

```python
def compute(..., already_paid_this_year: int = 0):
    ...
    remaining = max(0, (rule.annual_limit or 0) - already_paid_this_year)
```

매개변수는 있었다. 그런데 **오케스트레이터가 한 번도 넘기지 않았다.**
언제나 0이 들어갔다.

`0`은 "모른다"가 아니라 **"올해 아무것도 안 받았다"** 는 주장이다. 연간
한도를 이미 다 쓴 계약에도 한도가 통째로 남아 있는 것처럼 계산했다.

이건 018의 공제 항 누락, 019의 통원 비율과 같은 모양이다 — **비어 있는
값을 유리한 쪽 기본값으로 채워 두고 계산했다고 말했다.**

## 계약 상태는 이 시스템에 없다

올해 기지급액과 통원 횟수는 약관에 적혀 있지 않다. 청구인이 적는 것도
아니다. **보험사 시스템이 아는 값**이다.

그래서 저장소를 만들지 않았다. 청구가 들고 오게 했다.

```python
class ClaimHistory(BaseModel):
    """그 계약·그 보장종목의 올해 누적. 보험사 시스템이 준다."""
    paid_this_year: int = 0
    outpatient_visits_this_year: int = 0
```

**없으면 없는 대로 둔다.** `None`이면 계산기가 못 정한 항목의 이름을
돌려주고(`missing`), 그 금액을 지급액이 아니라 **상한**이라고 말한다.
notes/018에서 건강보험 본인부담률에 쓴 것과 같은 규칙이다 — 누락된 항이
전부 **과다지급 방향**이므로 상한이 맞다.

`extract_claim`은 이 값을 서술에서 뽑지 않는다. 뽑을 수 없는 것을 뽑는
척하지 않는다.

## 덤으로 또 하나 — 급여 통원에도 1회 한도가 있었다

제5조를 다시 읽다가 봤다.

> ⑤ 제3조에서 정한 **통원**의 경우 (1)상해급여 또는 (2)질병급여 각각에
> 대하여 **통원 1회당 20만원 이내**에서 회사가 정한 금액 중 계약자가
> 선택한 금액의 한도 내에서 보상합니다.

notes/017에서 이 한도를 **특약에만** 넣었다. 특약1·2의 제5조 ③을 읽고
"특약의 축"이라고 적었는데, 급여 제5조 ⑤에도 똑같이 있었다. 019에서
"특약을 읽고 급여도 그럴 것이라 가정했다"고 반성했는데 이번엔 **반대
방향으로** 같은 실수를 했다.

규모를 쟀다.

| 급여 통원 청구 | 본인부담률 | 고치기 전 | 한도 적용 | 과다 |
|---:|---:|---:|---:|---:|
| 300,000 | 30% | 210,000 | 200,000 | 10,000 |
| 500,000 | 30% | 350,000 | 200,000 | 150,000 |
| **1,000,000** | 30% | **700,000** | **200,000** | **500,000** |
| 2,000,000 | 60% | 800,000 | 200,000 | 600,000 |

100만원 통원 청구에서 **50만원 과다지급**이었다.

## 연간 통원 횟수

제5조 ③이 정하는 횟수 한도도 값으로 넣었다.

| 상품 / 항목 | 연간 한도 |
|---|---|
| 특약1 (1)(2) | 통원 100회 |
| 특약2 (1)(2) | 통원 100일 |
| 특약1 3대비급여 — 근골격계·체외충격파 | 50회 |
| 특약1 3대비급여 — 주사료 | 50회 |

다 쓴 계약은 그 해에 더 받지 못한다. 이것도 누적을 알아야 판정된다 —
모르면 상한이다.

## 데모가 어떻게 바뀌었나

**CLM-006** 급여 실손 / 폐렴 6일 입원 / 150만원 — 누적을 모른다

```
보상비율 80% / 연간한도 잔액 50,000,000원 이내
  / 올해 기지급액을 확인하지 못해 이 금액은 상한이다
-> HUMAN_REVIEW  0원  (가드레일 amount_upper_bound)
```

전에는 `PARTIAL 1,200,000원`이었다. **한도를 이미 다 쓴 계약일 수도 있는데
그걸 모른 채 지급액을 말하고 있었다.**

**CLM-010** 급여 실손 / 폐렴 5일 입원 / 200만원 — **올해 150만원 기지급**

```
보상비율 80% / 연간한도 잔액 48,500,000원 이내
-> PARTIAL  1,600,000원
```

누적을 알려 주면 그대로 지급액이 나온다. 잔액이 5천만원이 아니라
4,850만원으로 줄어 있는 것이 보인다.

**CLM-011** 특약1 / 비급여 항암 통원 / 40만원 — **올해 통원 100회 소진**

```
통원 공제 120,000원 / 통원 1회 한도 200,000원으로 제한
  / 올해 통원 100회로 연간 한도 100회를 이미 채웠다
-> 지급액 0
```

## 측정

합성 청구 195건. 넷 중 하나는 일부러 누적을 비워 두었다 — 그 경로도
실제로 쓰이기 때문이다.

| | 이전 | 누적을 안 넘길 때 | **이후** |
|---|---:|---:|---:|
| `PARTIAL` | 28 | 0 | **35** |
| 가드레일 `amount_upper_bound` | 13 | 41 | **8** |
| 청구 1건당 지연 | 1.0ms | — | **1.3ms** |

가운데 칸이 이 변경의 진짜 의미다. **계약 상태를 안 주면 지급액이 하나도
안 나온다.** 그게 맞다 — 모르면 말하지 않는 것이다.

지연이 1.0 → 1.3ms로 늘었다. 일이 늘어서다. 전보다 많은 청구가 금액산정을
끝까지 지나 `PARTIAL`까지 간다.

## 아직 없는 것

**제5조 ④ 자기부담 200만원 상한.**

> 입원의 경우 … 본인부담금의 20%에 해당하는 금액이 계약일 또는 매년
> 계약해당일부터 기산하여 **연간 200만원을 초과하는 경우 그 초과금액은**
> 제1항의 한도내에서 **보상합니다**

이건 방향이 반대다. 자기부담 누적이 200만원을 넘으면 그 뒤로는 **더 많이**
지급한다. 그래서 이 값을 모르면 우리 계산은 **과소**지급이 되고, 상한이
아니라 하한이 된다.

`is_upper_bound`는 과다지급 방향의 누락만 담는 표시다. 방향이 다른 누락을
같은 깃발에 얹으면 그 깃발의 뜻이 흐려진다. 그래서 넣지 않고 `note`에
남겼다 — **틀린 이름표를 붙이느니 비워 두는 편이 낫다.**

284 passed.

## 배운 것

**기본값은 조용한 가정이다.** `already_paid_this_year: int = 0`은 타입도
맞고 테스트도 통과했다. 그 값이 "모른다"인지 "0이다"인지는 타입이 말해
주지 않는다.

이 프로젝트에서 같은 실패를 네 번 했다 — 감액계수 730일(019), 공제 세
번째 항(018), 통원 보상비율(019), 그리고 이번 기지급액. 넷 다 **없는 값을
있는 값처럼 두고 계산을 이어 간 것**이다.

`None`으로 두면 계산이 멈추고, 멈추면 보인다.
