# 040 — 같은 5단계를 LangGraph로 다시 짜고 둘을 맞대 봤다

[notes/037](037-jd-gap.md)에서 `LangChain·LangGraph`는 판정이 **없음**이었다.
공고 우대사항에 이름으로 적혀 있는 항목이다.

그렇다고 자체 오케스트레이터를 버리고 갈아타는 것은 이 프로젝트의 방식이
아니다. **둘을 같은 청구에 걸어 재는 것**이 방식이다. 갈아타는 것은 "써
봤다"가 되고, 맞대는 것은 "무엇이 나은지 안다"가 된다.

## 스텝 함수를 두 벌 만들지 않았다

[notes/036](036-pdf-layout.md)에서 PDF 파서를 만들 때 쓴 규칙 그대로다.

> PDF용 조문 규칙을 새로 쓰면 불일치가 나와도 원인을 못 가린다 —
> 레이아웃 탓인지 규칙 탓인지.

버전 확정·보장 탐색·면책 검증·금액 산정·가드레일은 **기존 함수를 그대로
부른다.** `graph_orchestrator.py`가 새로 쓰는 것은 **스텝을 잇는 방법**뿐이다.

덕분에 **라벨이 필요 없다.** 두 구현이 다른 답을 내면 그것은 정의상
오케스트레이션의 차이다. notes/033에서 "정답이 구성으로 정해진다"고 쓴
것과 같은 구조다.

## 결과

청구 195건(합성, 웜업 5 제외).

| 축 | 자체 | LangGraph |
|---|---:|---:|
| **판정 일치** | **195/195 = 100%** | |
| p50 지연 | **0.30ms** | 2.27ms |
| p95 지연 | **4.03ms** | 5.25ms |
| 오케스트레이션 줄 수 | **225** | 250 |
| 의존성 트리 | neo4j 4 | **79** |

판정·금액·판본·가드레일·근거 uid·사유 문구까지 전부 맞다. 판정 문자열만
맞춰 보면 "둘 다 DENIED인데 근거 조항이 다른" 경우를 놓치므로 증거까지 본다 —
이 시스템에서 근거는 산출물이다.

## 1. 부담은 배수가 아니라 상수다

p50만 보면 **7.6배**다. 이 숫자만 적으면 오해를 만든다.

| | 자체 | LangGraph | 차 |
|---|---:|---:|---:|
| p50 | 0.30ms | 2.27ms | **+1.97ms** |
| p95 | 4.03ms | 5.25ms | **+1.22ms** |

**차이가 배수가 아니라 +1~2ms로 거의 고정이다.** p95에서는 실제 조회가
시간을 먹으므로 비율이 1.3배로 줄어든다. 즉 LangGraph가 스텝마다 쓰는
비용은 일정하고, 7.6배라는 수는 **이 시스템이 유난히 빠르기 때문에** 나온다.

이걸 어떻게 읽을지는 대상에 달렸다. 심사 한 건이 0.30ms인 이 시스템에서는
+1.97ms가 7배지만, LLM을 한 번이라도 부르는 에이전트에서는 **측정이 안 되는
수준**이다. notes/012의 로컬 4B가 2,438ms였다 — 거기에 1.97ms를 더하는 것은
0.08%다.

> **프레임워크 비용은 "느리다/빠르다"가 아니라 "무엇에 견줘 느린가"다.**

## 2. 얻는 것은 속도가 아니라 구조다

여기서 한 군데를 **일부러 다르게** 짰고, 그게 이 노트에서 제일 중요하다.

**이 비교를 시작할 때** 자체 구현은 종료 지점이 넷이었고 넷 다
`_finalize`(가드레일)를 불렀다.

```python
    if version is None:
        return _finalize(...)      # 가드레일 1
    if not coverage_evidence:
        return _finalize(...)      # 가드레일 2
    if certain:
        return _finalize(...)      # 가드레일 3
    return _finalize(...)          # 가드레일 4
```

**이건 약속이지 구조가 아니다.** 다섯 번째 `return`을 쓰면서 `_finalize`를
빠뜨리면 그 경로만 가드레일 없이 나간다. 그리고 그 사실은 판정 결과를
봐서는 안 보인다 — 가드레일은 대부분의 청구에서 발동하지 않으니까.

LangGraph 쪽은 종료 노드가 **초안만** 채우고 엣지 넷이 전부 `검증심판`으로
모인다.

```
금액산정 ─┐
버전없음 ─┼─> 검증심판 ─> END
보장없음 ─┤
부지급  ─┘
```

가드레일을 건너뛰려면 **엣지를 그려야** 하고, 엣지는 `build()`에 한눈에
보인다. 그리고 그 성질을 테스트로 못 박을 수 있다 —
`test_no_terminal_reaches_end_without_the_verdict_node`는 컴파일된 그래프의
엣지를 읽어 `__end__`로 가는 노드가 `검증심판` 하나뿐인지 확인한다.
**DB 없이 도는 테스트다.**

[notes/039](039-access-control.md)를 쓰고 난 직후라 이 성질이 더 값어치
있어 보인다. 거기서 잰 것이 정확히 "게이트를 한 곳에만 걸면 94.5%가 샌다"
였다. 경로가 여럿일 때 **모든 경로가 게이트를 지나는지를 사람이 기억하는
방식**은 이 프로젝트에서 이미 두 번 실패했다(notes/023, notes/039).

구조를 바꾸고도 판정은 195/195로 같다. 다르면 구조 변경이 동작을 바꾼
것이므로 비교가 아니라 사고인데, 그렇지 않았다.

**그리고 이 절을 쓰고 나서 자체 구현도 같은 모양으로 고쳤다.** 아래
"그래서 무엇을 쓰나"를 보라 — 위 코드 조각은 고치기 **전**의 모습이다.

## 3. 대가는 상태 선언과 의존성이다

**상태를 타입으로 선언해야 한다.** 자체 구현에서 지역 변수였던 것이
`AdjudicationState`의 필드가 된다. 선언을 빠뜨리면 다음 노드에서 조용히
`None`이 되고, 이건 `if ... return`에는 없던 실패 방식이다. 225 대 250에서
남는 25줄의 상당 부분이 이 선언이다.

**의존성이 4개에서 79개가 된다.** 폐쇄망 반입 심사에서 이건 그냥 숫자가
아니다. 실제로 새로 설치된 것이 15개고, 그 안에 이런 것이 있다.

| | |
|---|---|
| `langsmith` | LangChain의 관측 SDK |
| `httpx2`, `websockets`, `requests-toolbelt` | 네트워크 클라이언트 |
| `zstandard`, `orjson`, `ormsgpack`, `xxhash` | 직렬화·압축 |

`langsmith`는 확인해 봤다. **기본값은 꺼져 있다** —
`langsmith.utils.tracing_is_enabled()`가 `False`이고,
`LANGSMITH_TRACING`/`LANGCHAIN_TRACING_V2`가 없으면 아무 데도 보내지
않는다. 다만 **pytest 플러그인으로 자동 등록된다**(`plugins: langsmith-0.14.1`).

전송하지 않는다는 것과 반입 심사를 통과한다는 것은 다른 말이다. 폐쇄망에
들일 때는 "기본값이 꺼져 있다"가 아니라 "꺼져 있음을 어떻게 보증하느냐"를
답해야 하고, 그 답에 패키지 15개가 딸려 온다.

## 그래서 무엇을 쓰나

**자체 오케스트레이터를 그대로 쓴다.** 코드는 둘 다 남긴다.

근거는 이렇다. 이 흐름은 **분기가 전부 종료로 가는 직선**이다. 합류도 없고
되돌아가지도 않고 병렬도 없다. LangGraph가 잘하는 것(순환, 사람 개입 지점,
체크포인트에서 재개, 병렬 분기 합류)이 여기에 하나도 없다. 그림으로 그려도
`if` 넷보다 더 보여 주는 것이 없다.

**바뀌는 조건을 적어 둔다.** notes/031·038에서 쓴 것과 같은 식이다.

- 스텝이 되돌아가거나(재심사 루프) 사람 개입 뒤 **같은 자리에서 재개**해야
  하면 — 체크포인트를 직접 만드는 것보다 낫다. `revise_claim`이 지금은
  처음부터 다시 도는데(notes/032), 청구가 무거워지면 이 축이 살아난다.
- 스텝이 병렬로 갈라졌다 합류하면 — `_keep_last` 대신 진짜 병합 규칙이
  필요해지고, 그걸 손으로 짜는 것은 지루하고 틀리기 쉽다.
- LLM을 부르는 스텝이 생기면 — 2ms가 측정 한계 아래로 내려간다.

**하나는 가져왔다.** 가드레일을 **모든 종료 경로가 지나는 한 지점**으로
모으는 구조는 프레임워크 없이도 된다. 자체 `orchestrator`를 고쳤다 —
`_run`이 `_Draft`를 만들고, `_finalize`는 `adjudicate`의 마지막 한 줄에서만
불린다. 네 군데가 한 군데가 됐다.

바꾸고 다시 쟀다. **195/195 그대로다.** 판정을 바꾸지 않았다는 것을
`compare.py`가 확인해 줬다 — 비교 하네스가 리팩터링의 안전망 노릇을 했다.

| | 전 | 후 |
|---|---:|---:|
| `_finalize` 호출 지점 | 4 | **1** |
| 자체 오케스트레이션 줄 | 198 | 225 |
| 판정 일치 | — | 195/195 |

줄 수는 27줄 늘었다. `_Draft`를 선언하는 값이고, **그 대가로 "빠뜨릴 수
있는 자리"가 넷에서 하나가 됐다.** `test_guardrails_run_at_exactly_one_place`가
되돌아가는 것을 막는다.

**프레임워크에서 배운 것을 프레임워크 없이 쓰는 쪽**이 이 프로젝트에 맞는다.
LangGraph를 들이지 않고도 LangGraph가 강제하던 성질을 얻었다.

## 남은 것

- 비교가 **행복 경로 위주**다. 합성 청구 195건에 DB 장애나 타임아웃이 없다.
  스텝이 실패할 때 두 구현이 어떻게 다른지는 재지 않았다 — LangGraph는
  거기서 다를 여지가 크다(재시도 정책, 부분 실패 상태).
- `langgraph` extra를 기본 묶음에 넣지 않았다. 비교용이다.
